# Построение игрового мира

## 1. Цель визуального подхода

Мир должен выглядеть как компактная читаемая voxel-диорама лунной поверхности. Геометрия строится из блоков и простых низкополигональных форм. Основной приоритет — силуэт, понятные масштабы, игровые зоны и читаемость объектов с фиксированной изометрической камеры.

Материалы преимущественно матовые и однотонные. Цветом выделяются интерактивные категории: ресурсы, предупреждения, навигационные элементы и подсветка выбора.

## 2. Пространственная модель

Рекомендуемая система координат:
- X — восток/запад.
- Z — север/юг по поверхности.
- Y — высота.
- Игровые объекты хранят мировые координаты X/Z и вычисляют высоту поверхности отдельно.

Не смешивать координаты модели, экранные координаты и координаты указателя мыши. Все преобразования должны проходить через функции камеры/проекции.

## 3. Рельеф

Текущая сцена использует лунный кратер с неглубокой чашей и неровным поднятым краем. В прототипе это стилизованная игровая площадка, а не геологически точная симуляция.

Рекомендуемый способ построения:
1. Определить функцию высоты поверхности `heightAt(x,z)`.
2. Задать радиус чаши, глубину, ширину перехода и профиль края.
3. Сформировать поверхность из сетки или набора voxel-столбцов.
4. Для каждого объекта получать Y через общую функцию рельефа, а не назначать высоту вручную.
5. Добавить каменные выступы и отдельные крупные блоки по заранее заданному seed.

Важное требование: одна и та же координата X/Z должна давать согласованную высоту для лунохода, камней, построек, месторождений и маркеров.

## 4. Детерминированное размещение объектов

Ресурсы и декоративные камни должны размещаться детерминированно по seed. Это обеспечивает повторяемость тестов и одинаковую стартовую сцену.

Для месторождений:
- генерировать список точек вокруг игровой зоны, избегая стартовой площадки и маршрута выезда;
- тип ресурса задавать данными: Fe, Ti или Si;
- тело месторождения формировать группой блоков разного размера/высоты;
- над группой показывать маяк/цветовой индикатор;
- хранить ID узла, тип, координаты, доступное количество и состояние истощения.

Текущий код использует детерминированное распределение месторождений по спирали и показывает их на радаре. Это подходит для прототипа; для большого мира генерацию нужно будет разделить на чанки.

## 5. Объекты базы

Постройки должны быть отдельными сущностями, а не частью монолитной функции рисования всей сцены. У каждой сущности должны быть:
- уникальный ID;
- тип;
- координаты;
- поворот;
- footprint/габариты;
- уровень улучшения;
- состояние: чертёж, строится, завершено, демонтируется, повреждено;
- время начала/окончания процесса.

Рендерер получает данные сущности и рисует соответствующую модель. Система строительства не должна напрямую создавать произвольные меши и менять рендерер.

## 6. Изометрическая камера

- Камера фиксирована по азимуту и углу наклона.
- Камера следует за луноходом с плавным сглаживанием.
- Не использовать вращение камеры мышью как основное управление.
- При строительстве можно предусмотреть отдельный обзор базы, но это явный режим, не случайное изменение камеры.
- Проекция должна иметь единый набор функций: world-to-screen, screen-to-world ray, hit-test.

## 7. Коллизии и навигация

Рекомендуется хранить коллайдеры в данных объектов. Для текущего масштаба можно использовать круги/прямоугольники в плоскости X/Z; позже — пространственную сетку или физический движок.

Проверки должны быть единообразными для:
- лунохода;
- строящихся объектов;
- завершённых построек;
- камней;
- стен и опор гаража;
- границ доступной зоны.

Нельзя иметь одну логику столкновений для лунохода и другую, противоречащую ей, для размещения зданий.

## 8. Производительность

Для статичного прототипа допустимо отрисовывать ограниченное число объектов напрямую. Для расширения мира:
- объединять статическую геометрию по материалам;
- использовать чанки и отсечение невидимых областей;
- обновлять динамические объекты отдельно от статического окружения;
- не пересоздавать геометрию мира каждый кадр;
- иметь детерминированные ID чанков и объектов.

Для мультиплеера клиент получает только релевантные области мира, а не полное состояние всех 1000+ игроков и объектов.
