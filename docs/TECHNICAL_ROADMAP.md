# Техническая архитектура и дорожная карта

## 1. Слои клиентского приложения

Рекомендуемое разделение:

- `world/` — рельеф, чанки, окружение, ресурсы, spatial queries.
- `render/` — WebGL renderer, камера, геометрия, материалы, эффекты.
- `entities/` — луноход, постройки, месторождения, интерактивные объекты.
- `systems/` — движение, коллизии, добыча, строительство, энергия, прогресс.
- `ui/` — HUD, модальные окна, каталог, инвентарь, радар.
- `data/` — конфигурации объектов, рецепты, уровни, стоимость и баланс.
- `persistence/` — локальные сохранения и миграции.
- `network/` — будущий WebSocket-клиент и синхронизация.

Это целевая структура. Не следует механически переносить всё в папки одним большим рефакторингом: сначала выделить интерфейсы и покрыть тестами текущие функции.

## 2. Модель сущностей

Каждый объект мира имеет стабильный ID и тип. Пример записи постройки:

```json
{
  "id": "building-unique-id",
  "type": "solar",
  "x": 12.5,
  "z": -4,
  "rotation": 1,
  "level": 1,
  "status": "completed",
  "createdAt": 0
}
```

Для операций строительства отдельно хранить:
- ID операции;
- ID игрока;
- ID проекта постройки;
- цену/списанные ресурсы;
- время начала и окончания;
- состояние;
- причину отмены/ошибки.

## 3. Локальное сохранение

Текущий прототип использует localStorage. Для надёжной миграции:
- версионировать схему сохранения;
- валидировать входящие данные;
- не читать старые данные как доверенные;
- делать миграцию отдельной функцией;
- сохранять резервную копию перед разрушительной миграцией;
- не менять ID сущностей без необходимости.

localStorage пригоден для одиночного прототипа, но не для синхронизации общей игры.

## 4. Будущая серверная архитектура

Целевая система:
- Node.js сервер;
- WebSocket для real-time событий;
- PostgreSQL для постоянного состояния;
- серверная авторитетность движения, добычи, строительства, экономики и прогресса;
- админ-панель и JSON export/import как инструмент управления данными.

Ключевое правило: клиент отправляет намерения, сервер валидирует их и сохраняет итог. Клиент может показывать предварительный ghost и оптимистичный UI, но окончательное подтверждение операции приходит от сервера.

## 5. Масштаб 1000+ игроков

Для 1000+ игроков в одном мире нельзя каждый тик отправлять каждому клиенту полное состояние всех объектов и игроков.

Нужны:
- spatial partitioning (сетка/чанки/сектора);
- interest management: клиент подписан только на ближайшие/релевантные области;
- отдельные частоты обновления для игроков, транспорта, окружения и редких событий;
- бинарный/компактный формат сообщений при необходимости;
- server tick budget и backpressure;
- контроль очередей и лимиты частоты команд;
- persistence не на каждый кадр, а по событиям/пакетам изменений;
- метрики CPU, памяти, сетевого трафика, задержки и размера очередей;
- нагрузочные тесты с моделированием движения и строительных операций.

Нельзя гарантировать 1000+ игроков одной только структурой кода; результат зависит от профиля нагрузки, частоты обновлений, размера мира, hardware и сетевой топологии.

## 6. Этапы реализации

1. **Стабилизация одиночного прототипа:** синтаксис, браузерные сценарии, сохранение, resize, ошибки консоли.
2. **Строительный редактор:** точный ray-plane/heightfield picking, ghost preview, footprint collision, snap, rotation, undo/redo.
3. **Игровая экономика:** уровни, кредиты, ресурсы, строительство и демонтаж по таймерам, улучшения.
4. **Стартовая прогрессия:** восстановление коммуникационной станции, задачи и первые открытия.
5. **Энергетика:** солнечные панели, энергобаланс, потребители и накопители.
6. **Рефакторинг данных:** единые каталоги объектов и версионированные сохранения.
7. **Серверная вертикаль:** аккаунт, WebSocket, авторитетные команды, PostgreSQL.
8. **Мультиплеер:** синхронизация ближайших игроков/объектов, interest management.
9. **Нагрузочная оптимизация:** измерения и тесты до целевой нагрузки 1000+.

## 7. Проверки перед публикацией этапа

- JavaScript syntax check.
- Проверка ссылок на скрипты, CSS, изображения и HTML IDs.
- Проверка основных сценариев вручную в браузере.
- Проверка узкого и широкого экрана.
- Проверка загрузки старых сохранений.
- Проверка повторного открытия страницы и восстановления состояния.
- Для серверной версии — unit/integration tests, транзакционные тесты и нагрузочные сценарии.

Статус проверки должен быть описан честно: синтаксическая проверка не означает, что игровой сценарий визуально проверен.
